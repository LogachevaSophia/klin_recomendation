# Движок исполнения визуальных алгоритмов принятия решений в медицинских системах

## Аннотация

Разработан программный модуль (движок исполнения), который преобразует визуальные схемы алгоритмов принятия решений, созданные в редакторе на базе React Flow, в исполняемые последовательности действий. Движок реализует интерпретацию графовых структур с поддержкой условных переходов, циклов, подпроцессов и динамического обновления данных пациента в процессе выполнения.

## 1. Введение

### 1.1. Проблематика

В медицинских информационных системах существует необходимость в визуальном представлении клинических алгоритмов принятия решений. Традиционные подходы требуют ручного программирования логики, что затрудняет создание и модификацию алгоритмов врачами без навыков программирования. Требуется решение, которое позволит:

1. Визуально описывать алгоритмы принятия решений
2. Автоматически исполнять эти алгоритмы на основе данных пациента
3. Поддерживать сложные структуры: условия, циклы, подпроцессы
4. Обеспечивать динамическое обновление данных в процессе выполнения

### 1.2. Цель работы

Разработка движка исполнения, который интерпретирует визуальные схемы алгоритмов и выполняет их логику, принимая решения на основе данных пациента аналогично тому, как это делает врач.

## 2. Архитектура решения

### 2.1. Общая архитектура

Движок исполнения построен на основе интерпретатора графовых структур. Входными данными является визуальная схема, представленная в виде ориентированного графа, где:
- **Узлы (nodes)** представляют действия, условия или подпроцессы
- **Рёбра (edges)** определяют последовательность выполнения и условия переходов

### 2.2. Компонентная структура

Система состоит из следующих основных компонентов:

#### 2.2.1. ExecutionEngine (Основной движок)

**Назначение:** Управляет выполнением алгоритма, координирует работу всех компонентов.

**Основные функции:**
- Поиск начального узла в графе
- Последовательное выполнение узлов
- Управление контекстом выполнения
- Обработка ошибок и защита от бесконечных циклов
- Управление подпроцессами и циклами

**Алгоритм выполнения:**
```
1. Загрузка схемы процесса
2. Инициализация контекста выполнения
3. Поиск начального узла (узел без входящих рёбер или с меткой "Начало")
4. Цикл выполнения:
   a. Выполнение текущего узла через соответствующий обработчик
   b. Получение следующего узла на основе результата выполнения
   c. Проверка условий завершения
   d. Защита от бесконечных циклов (лимит посещений узла)
5. Возврат результата выполнения
```

**Защита от бесконечных циклов:**
- Отслеживание количества посещений каждого узла (лимит: 50 посещений)
- Максимальное количество шагов выполнения (по умолчанию: 1000)
- Таймаут выполнения (по умолчанию: 30 секунд)

#### 2.2.2. NodeHandler (Обработчики узлов)

**Назначение:** Реализуют логику выполнения для различных типов узлов.

**Типы обработчиков:**

**ActionNodeHandler** — обработка действий
- Выполняет действия, указанные в узле
- Обрабатывает атрибуты узла для создания переменных
- Поддерживает обновление данных пациента через атрибуты с префиксом `patient.` или `update.`
- Проверяет наличие требуемых данных через атрибуты с префиксом `require:` или `требуется:`
- При отсутствии требуемых данных приостанавливает выполнение

**ConditionNodeHandler** — обработка условий
- Извлекает условие из атрибутов узла или метки
- Оценивает условие через ConditionEvaluator
- Выбирает путь выполнения на основе результата (ДА/НЕТ)
- Возвращает информацию о результате условия

**SubprocessNodeHandler** — обработка подпроцессов
- Загружает подпроцесс по идентификатору
- Выполняет подпроцесс рекурсивно через ExecutionEngine
- Объединяет переменные и историю выполнения с родительским контекстом
- Использует ссылку на данные пациента для обеспечения видимости изменений

**LoopNodeHandler** — обработка циклов
- Определяет параметры цикла (подпроцесс, условие выхода, максимальное количество итераций)
- Выполняет подпроцесс цикла в цикле
- Проверяет условие выхода перед каждой итерацией
- Сохраняет снимки данных пациента на каждой итерации

**StartNodeHandler** — начальный узел
- Передаёт управление следующему узлу без выполнения действий

**FinishNodeHandler** — конечный узел
- Завершает выполнение алгоритма

**NodeHandlerFactory** — фабрика обработчиков
- Создаёт соответствующий обработчик на основе типа узла
- Использует паттерн Factory для инкапсуляции логики создания

#### 2.2.3. ConditionEvaluator (Оценщик условий)

**Назначение:** Оценивает логические условия на основе данных пациента.

**Алгоритм оценки:**
```
1. Нормализация выражения (удаление знаков вопроса, обработка русского текста)
2. Обработка специальных паттернов:
   - "АД < 140/90" → проверка обоих значений давления
   - "АД стабилизировалось < 140/90" → проверка стабилизации
   - "Есть 38.5" → проверка температуры
   - "Есть кашель" → проверка наличия симптома
3. Обработка специальных функций (has, exists)
4. Замена обращений к данным пациента на их значения
5. Замена переменных контекста на их значения
6. Безопасное выполнение выражения
```

**Поддерживаемые операторы:**
- Сравнение: `==`, `!=`, `<`, `>`, `<=`, `>=`
- Логические: `&&`, `||`, `!`
- Функции: `has('key')`, `exists('key')`

**Обработка русских условий:**
- Автоматическое распознавание русских терминов (АД, температура, кашель)
- Преобразование естественного языка в логические выражения
- Поддержка вопросов в условиях ("АД стабилизировалось < 140/90?")

**Безопасное выполнение:**
- Использование Function constructor для изоляции выполнения
- Обработка ошибок с возвратом false по умолчанию

#### 2.2.4. ExecutionContext (Контекст выполнения)

**Назначение:** Хранит состояние выполнения алгоритма.

**Структура:**
```typescript
{
  patientData: PatientData,           // Данные пациента
  variables: Record<string, any>,      // Переменные, созданные во время выполнения
  executionHistory: ExecutionStep[],   // История выполнения
  currentPath: string[],               // Путь пройденных узлов
  updatePatientData?: Function         // Функция для обновления данных
}
```

**Особенности:**
- Данные пациента могут обновляться во время выполнения
- Переменные создаются через атрибуты узлов
- История выполнения позволяет отследить весь путь алгоритма

### 2.3. Типы данных

#### 2.3.1. PatientData
Динамическая структура для хранения данных пациента:
```typescript
{
  [key: string]: any  // Поля: age, temperature, bloodPressure, symptoms и т.д.
}
```

#### 2.3.2. ExecutionResult
Результат выполнения алгоритма:
```typescript
{
  success: boolean,              // Успешность выполнения
  finalNodeId?: string,         // ID финального узла
  steps: ExecutionStep[],        // История выполнения
  finalVariables: Record<string, any>, // Финальные переменные
  error?: string,                // Ошибка, если была
  executionTime: number,         // Время выполнения в мс
  paused?: boolean,              // Выполнение приостановлено
  requiredData?: string[],       // Требуемые данные
  message?: string               // Сообщение для пользователя
}
```

#### 2.3.3. ExecutionStep
Шаг выполнения алгоритма:
```typescript
{
  nodeId: string,                // ID узла
  nodeType: string,              // Тип узла
  nodeLabel: string,             // Название узла
  timestamp: number,             // Время выполнения
  result?: any,                  // Результат выполнения
  conditionResult?: boolean,     // Результат условия
  error?: string                 // Ошибка, если была
}
```

## 3. Алгоритмы и методы

### 3.1. Алгоритм выполнения узла

```
ВХОД: node, context, edges
ВЫХОД: ExecutionStep

1. Получить обработчик узла через NodeHandlerFactory
2. Выполнить узел через обработчик
3. Если узел - подпроцесс:
   a. Выполнить подпроцесс рекурсивно
   b. Объединить результаты с родительским контекстом
4. Если узел - цикл:
   a. Выполнить цикл через executeLoop
   b. Сохранить результаты итераций
5. Создать ExecutionStep с результатами
6. ВЕРНУТЬ ExecutionStep
```

### 3.2. Алгоритм выполнения цикла

```
ВХОД: loopSubprocessId, loopCondition, maxIterations, context
ВЫХОД: {iterations, loopResults}

1. Инициализация: iteration = 0, loopResults = []
2. ПОКА iteration < maxIterations:
   a. iteration++
   b. ЕСЛИ loopCondition существует:
      - Оценить условие через ConditionEvaluator
      - ЕСЛИ условие выполнено: ВЫХОД из цикла
   c. Выполнить подпроцесс цикла
   d. Сохранить снимок данных пациента
   e. ЕСЛИ подпроцесс завершился с ошибкой: ВЫХОД
   f. ЕСЛИ есть callback onPatientDataUpdate:
      - Вызвать callback для обновления данных
3. ВЕРНУТЬ {iterations, loopResults}
```

### 3.3. Алгоритм оценки условия

```
ВХОД: condition (строка), context
ВЫХОД: boolean

1. Нормализовать выражение:
   a. Удалить знаки вопроса
   b. Обработать паттерны русского языка
   c. Преобразовать естественный язык в логические выражения
2. Обработать специальные функции (has, exists)
3. Заменить обращения к данным пациента на значения
4. Заменить переменные контекста на значения
5. Безопасно выполнить выражение
6. ВЕРНУТЬ результат (boolean)
```

### 3.4. Алгоритм обработки подпроцесса

```
ВХОД: subprocessId, parentContext
ВЫХОД: ExecutionResult

1. Создать контекст подпроцесса:
   - Наследовать данные пациента (ссылка, не копия)
   - Наследовать переменные (копия)
   - Наследовать функцию обновления данных
2. Сохранить текущий активный процесс
3. Выполнить подпроцесс рекурсивно через execute()
4. Объединить переменные с родительским контекстом
5. Объединить историю выполнения
6. Восстановить предыдущий активный процесс
7. ВЕРНУТЬ результат
```

## 4. Особенности реализации

### 4.1. Динамическое обновление данных пациента

**Проблема:** В медицинских алгоритмах данные пациента могут изменяться во время выполнения (например, после приёма препарата изменяется давление).

**Решение:**
1. **Через атрибуты узлов:** Атрибуты с префиксом `patient.` или `update.` обновляют данные пациента
2. **Через callback:** `onPatientDataUpdate` позволяет симулировать изменения данных
3. **Через запрос данных:** Атрибуты с префиксом `require:` приостанавливают выполнение для ввода данных

**Пример обновления через атрибуты:**
```
Атрибут:
  name: "patient.bloodPressure.systolic"
  value: "130"
```

### 4.2. Пауза выполнения и запрос данных

**Проблема:** Алгоритм может требовать ввода данных во время выполнения (например, измерение давления).

**Решение:**
1. ActionNodeHandler проверяет атрибуты с префиксом `require:`
2. Если требуемые поля отсутствуют в данных пациента, выполнение приостанавливается
3. Возвращается результат с флагом `paused: true` и списком требуемых полей
4. UI показывает форму для ввода данных
5. После ввода выполнение продолжается с обновлёнными данными

**Пример:**
```
Атрибут:
  name: "require:bloodPressure.systolic"
  value: "Введите систолическое давление"
```

### 4.3. Обработка русских условий

**Проблема:** Условия могут быть написаны на русском языке в естественной форме.

**Решение:**
- Нормализация выражений с распознаванием русских паттернов
- Преобразование естественного языка в логические выражения
- Поддержка различных вариантов написания (АД, артериальное давление)

**Примеры обработки:**
- "АД стабилизировалось < 140/90?" → `(systolic < 140 && diastolic < 90)`
- "Есть 38.5" → `temperature == 38.5`
- "Есть кашель" → `has('cough')`

### 4.4. Защита от бесконечных циклов

**Многоуровневая защита:**
1. **Отслеживание посещений узлов:** Если узел посещён более 50 раз, выполнение останавливается
2. **Лимит шагов:** Максимальное количество шагов (по умолчанию 1000)
3. **Таймаут:** Максимальное время выполнения (по умолчанию 30 секунд)
4. **Лимит итераций цикла:** Максимальное количество итераций (по умолчанию 100)

### 4.5. Рекурсивное выполнение подпроцессов

**Особенности:**
- Подпроцессы выполняются рекурсивно через тот же ExecutionEngine
- Данные пациента передаются по ссылке для обеспечения видимости изменений
- Переменные наследуются, но изолированы на уровне подпроцесса
- История выполнения объединяется с родительским контекстом

## 5. Примеры использования

### 5.1. Простой алгоритм

**Схема:**
```
Start → Action: "Проверить температуру" → Condition: "Температура > 37.5?" 
  → [ДА] Action: "Назначить жаропонижающее" → Finish
  → [НЕТ] Finish
```

**Данные пациента:**
```json
{
  "temperature": 38.5
}
```

**Результат:** Выполняется путь "ДА", назначается жаропонижающее.

### 5.2. Алгоритм с циклом

**Схема:**
```
Start → Loop: "Мониторинг давления"
  Условие выхода: "bloodPressure.systolic < 140 && bloodPressure.diastolic < 90"
  Подпроцесс:
    - Action: "Измерить давление" (require:bloodPressure.systolic, require:bloodPressure.diastolic)
    - Action: "Принять препарат"
  → Condition: "Давление < 140/90?" → [ДА] Finish
```

**Данные пациента:**
```json
{
  "bloodPressure": {
    "systolic": 160,
    "diastolic": 95
  }
}
```

**Результат:** Цикл выполняется до тех пор, пока пользователь не введёт данные давления, которые удовлетворяют условию выхода.

### 5.3. Алгоритм с подпроцессом

**Схема:**
```
Start → Action: "Начать диагностику" → Subprocess: "Лабораторные анализы"
  Подпроцесс:
    - Action: "Взять кровь"
    - Condition: "Анализ готов?" → [ДА] Action: "Получить результаты"
  → Action: "Оценить результаты" → Finish
```

**Результат:** Подпроцесс выполняется рекурсивно, результаты объединяются с основным процессом.

## 6. Технические детали

### 6.1. Технологический стек

- **Язык:** TypeScript
- **Платформа:** Node.js / Browser
- **Библиотеки:** 
  - React Flow (для визуализации)
  - MobX (для управления состоянием)
  - Gravity UI (для UI компонентов)

### 6.2. Производительность

- **Время выполнения:** Зависит от сложности алгоритма, обычно < 100ms для простых алгоритмов
- **Память:** Линейная зависимость от количества узлов и глубины подпроцессов
- **Масштабируемость:** Поддерживает алгоритмы с сотнями узлов

### 6.3. Безопасность

- **Изоляция выполнения:** Использование Function constructor для безопасного выполнения выражений
- **Валидация данных:** Проверка формата данных пациента
- **Обработка ошибок:** Graceful degradation с возвратом ошибок

## 7. Заключение

Разработанный движок исполнения позволяет преобразовывать визуальные схемы алгоритмов принятия решений в исполняемый код. Система поддерживает сложные структуры (условия, циклы, подпроцессы), динамическое обновление данных и паузу выполнения для запроса данных у пользователя.

**Основные достижения:**
1. Интерпретация визуальных графовых структур
2. Поддержка сложных алгоритмических конструкций
3. Обработка естественного языка в условиях
4. Динамическое обновление данных в процессе выполнения
5. Защита от бесконечных циклов и ошибок

**Применение:**
- Клинические алгоритмы принятия решений
- Протоколы лечения
- Диагностические алгоритмы
- Системы поддержки принятия решений

**Дальнейшие направления развития:**
- Оптимизация производительности для больших алгоритмов
- Расширение поддержки естественного языка
- Интеграция с медицинскими базами данных
- Визуализация выполнения алгоритма в реальном времени
