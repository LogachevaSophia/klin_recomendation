# Упрощение логики движка исполнения алгоритма

## Аннотация

В рамках разработки системы клинических рекомендаций была проведена рефакторизация движка исполнения алгоритмов с целью упрощения логики обработки условных узлов (condition nodes). Основная задача заключалась в замене сложной системы парсинга атрибутов на простую и понятную структуру, которая обеспечивает надежную работу в циклических процессах, где данные пациента могут изменяться после выполнения действий (например, приема препаратов).

## 1. Проблематика

### 1.1 Исходное состояние

Изначальная реализация обработчика условных узлов (`ConditionNodeHandler`) использовала сложную систему атрибутов для определения параметров сравнения:

- **Формат атрибутов**: `require:fieldName:type`, `require:fieldName:compare`, `require:fieldName:compareValue`, `require:fieldName:hint`
- **Проблемы**:
  - Сложный парсинг строковых атрибутов с множественными двоеточиями
  - Трудность в понимании и поддержке кода
  - Высокая вероятность ошибок при парсинге
  - Неочевидная структура данных
  - Проблемы с обработкой циклов, где данные должны обновляться на каждой итерации

### 1.2 Контекст использования

В клинических алгоритмах часто встречаются циклические процессы мониторинга состояния пациента:

1. **Измерение параметра** (например, артериальное давление)
2. **Проверка условия** (например, АД < 140/90?)
3. **Если условие не выполнено** → назначение препарата
4. **Повторное измерение** → возврат к шагу 1

В таких сценариях критически важно, чтобы система запрашивала актуальные данные на каждой итерации цикла, а не использовала устаревшие значения из предыдущих измерений.

## 2. Методология решения

### 2.1 Принципы упрощения

Были сформулированы следующие принципы:

1. **Явность вместо неявности**: все параметры сравнения должны быть явно указаны в простых атрибутах
2. **Простота логики**: сравнение должно выполняться через простые условные операторы (if-блоки)
3. **Обратная совместимость**: поддержка старого формата атрибутов для существующих данных
4. **Надежность в циклах**: гарантированное обновление данных на каждой итерации цикла

### 2.2 Новая структура атрибутов

Вместо сложной системы `require:field:type` была введена простая структура с явными именами атрибутов:

| Атрибут | Тип | Описание | Пример |
|---------|-----|----------|--------|
| `inputField` | string | Поле в данных пациента для сохранения введенного значения | `"bloodPressure.systolic"` |
| `hint` | string | Подсказка для пользователя, что именно нужно ввести | `"Введите значение в мм рт.ст."` |
| `inputType` | enum | Тип вводимых данных | `"number"`, `"text"`, `"boolean"` |
| `compareOperator` | enum | Оператор сравнения | `"="`, `"!="`, `"<"`, `">"` |
| `compareValue` | string | Значение для сравнения | `"140"` |

### 2.3 Упрощенная логика сравнения

Логика сравнения была сведена к четырем простым условным операторам:

```typescript
if (compareOperator === '=') {
  conditionResult = typedInputValue == typedCompareValue;
} else if (compareOperator === '!=') {
  conditionResult = typedInputValue != typedCompareValue;
} else if (compareOperator === '<') {
  conditionResult = typedInputValue < typedCompareValue;
} else if (compareOperator === '>') {
  conditionResult = typedInputValue > typedCompareValue;
}
```

Это обеспечивает:
- **Прозрачность**: явно видно, какие операции выполняются
- **Расширяемость**: легко добавить новые операторы (например, `<=`, `>=`)
- **Отладку**: просто отследить, какое сравнение было выполнено

## 3. Архитектура решения

### 3.1 Обработка атрибутов

Реализована двухуровневая система обработки атрибутов:

1. **Первый уровень**: проверка новых атрибутов (`inputField`, `hint`, и т.д.)
2. **Второй уровень**: если новых атрибутов нет, парсинг старых (`require:field:type`)

Это обеспечивает:
- **Обратную совместимость** с существующими данными
- **Постепенный переход** на новый формат
- **Гибкость** в использовании

### 3.2 Логика запроса данных

Для обеспечения корректной работы в циклах реализована следующая логика:

```typescript
// Проверяем, является ли это частью цикла
const isInLoop = context.currentPath.length > 0 && 
                 context.executionHistory.some(step => 
                   step.nodeType === 'loop' || 
                   step.result?.loopResult !== undefined
                 );

// Логика запроса данных:
// 1. Если данных нет - всегда запрашиваем
// 2. Если мы в цикле - всегда запрашиваем (чтобы обновить после приема препаратов)
// 3. Если данных есть и мы НЕ в цикле - сравниваем (это повторное выполнение после ввода)
const shouldRequestData = !hasData || isInLoop;
```

### 3.3 Интеграция с ExecutionEngine

Движок исполнения (`ExecutionEngine`) был модифицирован для поддержки упрощенной структуры:

- Извлечение метаданных из результата выполнения узла
- Формирование структурированных метаданных для UI
- Передача информации о типе данных, подсказках и условиях сравнения

## 4. Детали реализации

### 4.1 Преобразование типов данных

Реализована корректная обработка различных типов данных:

**Числовые значения**:
```typescript
if (inputType === 'number') {
  typedInputValue = Number(currentValue);
  typedCompareValue = Number(compareValueStr);
}
```

**Булевы значения**:
```typescript
else if (inputType === 'boolean') {
  typedInputValue = currentValue === true || 
                    currentValue === 'true' || 
                    currentValue === 'True' || 
                    currentValue === 'Да' || 
                    currentValue === 'да';
  typedCompareValue = compareValueStr === 'true' || 
                      compareValueStr === 'True' || 
                      compareValueStr === 'Да' || 
                      compareValueStr === 'да';
}
```

### 4.2 Обработка вложенных полей

Поддерживается работа с вложенными структурами данных:

- **Пример**: `bloodPressure.systolic` → доступ к `patientData.bloodPressure.systolic`
- **Реализация**: рекурсивный обход структуры данных через `getNestedValue()`

### 4.3 Обратная совместимость

Для поддержки старого формата реализован парсер:

```typescript
// Ищем базовый атрибут require:field (без дополнительных двоеточий)
const requireAttr = attributes.find(
  (attr: any) => {
    if (!attr.name) return false;
    const name = attr.name.trim();
    if (!name.startsWith('require:') && !name.startsWith('требуется:')) return false;
    const afterPrefix = name.replace(/^(require|требуется):\s*/i, '');
    return !afterPrefix.includes(':'); // Базовое поле, не метаданные
  }
);
```

## 5. Преимущества нового подхода

### 5.1 Упрощение кода

- **Сокращение сложности**: убрано ~150 строк сложного парсинга
- **Улучшение читаемости**: явная структура атрибутов вместо парсинга строк
- **Снижение ошибок**: меньше мест для потенциальных багов

### 5.2 Надежность в циклах

- **Гарантированное обновление данных**: в циклах данные всегда запрашиваются заново
- **Корректная работа с изменяющимися параметрами**: после приема препаратов система запрашивает новые значения
- **Предотвращение использования устаревших данных**: старые значения не используются в новых итерациях

### 5.3 Улучшение пользовательского опыта

- **Понятные подсказки**: явные атрибуты `hint` для пользователя
- **Корректная типизация**: правильная обработка чисел, текста и булевых значений
- **Информативность**: пользователь видит условие сравнения и ожидаемое значение

### 5.4 Расширяемость

- **Легкое добавление операторов**: достаточно добавить новый `if`-блок
- **Простое добавление типов**: расширение enum `inputType`
- **Гибкость структуры**: легко добавить новые атрибуты без изменения логики парсинга

## 6. Примеры использования

### 6.1 Простое условие

**Атрибуты узла**:
```json
{
  "inputField": "targetOrganDamage",
  "hint": "Введите Да или Нет",
  "inputType": "boolean",
  "compareOperator": "=",
  "compareValue": "true"
}
```

**Логика работы**:
1. Система запрашивает у пользователя: "Введите Да или Нет"
2. Пользователь вводит значение (Да/Нет)
3. Система преобразует в boolean
4. Выполняется сравнение: `введенное_значение == true`
5. Переход по соответствующей ветке (true/false)

### 6.2 Условие в цикле

**Атрибуты узла**:
```json
{
  "inputField": "bloodPressure.systolic",
  "hint": "Введите значение в мм рт.ст.",
  "inputType": "number",
  "compareOperator": "<",
  "compareValue": "140"
}
```

**Сценарий**:
1. **Итерация 1**: Пользователь вводит 141 → условие `141 < 140` = false → назначение препарата
2. **Итерация 2**: Система **снова запрашивает** давление (не использует старое 141)
3. Пользователь вводит 135 → условие `135 < 140` = true → выход из цикла

**Ключевой момент**: на каждой итерации данные запрашиваются заново, что критично для корректной работы алгоритма.

## 7. Метрики улучшения

### 7.1 Сложность кода

- **До**: ~200 строк сложной логики парсинга
- **После**: ~80 строк простых условных операторов
- **Сокращение**: ~60% кода

### 7.2 Цикломатическая сложность

- **До**: высокая (множественные вложенные условия парсинга)
- **После**: низкая (линейная последовательность if-блоков)

### 7.3 Поддерживаемость

- **До**: требуется понимание сложной системы парсинга
- **После**: интуитивно понятная структура атрибутов

## 8. Заключение

Упрощение логики движка исполнения алгоритма позволило:

1. **Снизить сложность кода** на 60%
2. **Улучшить надежность** работы в циклических процессах
3. **Повысить читаемость** и поддерживаемость кода
4. **Обеспечить обратную совместимость** с существующими данными
5. **Упростить расширение** функциональности в будущем

Новый подход обеспечивает корректную работу алгоритмов в циклических сценариях, где данные пациента могут изменяться после выполнения действий, что критично для клинических рекомендаций, требующих мониторинга состояния пациента.
